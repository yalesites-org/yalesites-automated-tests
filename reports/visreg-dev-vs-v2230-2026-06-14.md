# Visual Regression Report: dev (pre-release) vs v2230

**Date:** 2026-06-14
**Tooling:** Playwright `toHaveScreenshot` A/B comparison (`tests/all-vis-reg.spec.ts`)
**Branch:** `visreg-dev-vs-v2230` (in `yalesites-automated-tests`)

| | |
|---|---|
| **Baseline (currently released)** | https://dev-ys-yalesites-visreg-yale-edu.pantheonsite.io |
| **Candidate (new version)** | https://v2230-ys-yalesites-visreg-yale-edu.pantheonsite.io |
| **Pages compared** | 30 component test pages (`/component-pages-for-e2e-testing/*`) |
| **Browsers** | Chromium, Firefox, WebKit, Mobile Safari (iPhone 13 Mini) |
| **Total comparisons** | 120 (30 pages x 4 browsers) |
| **Diff threshold** | `maxDiffPixelRatio: 0.001` (strict; full-page, animations disabled) |

## Verdict

**No visual regressions found.** All 30 components render consistently between
the currently-released `dev` site and the `v2230` candidate across all browsers
where a stable screenshot could be captured.

Of 120 comparisons, 118 matched cleanly. The 3 that did not match on the first
attempt were each triaged and confirmed **not** to be release regressions:

| Page | Browser | Outcome | Classification |
|---|---|---|---|
| button-link | Chromium | Failed (all retries) | Transient server error on v2230 -- not a regression |
| video | Chromium | Flaky (passed on retry) | Third-party YouTube embed thumbnail load timing -- not a regression |
| view | WebKit | Failed to stabilize | Dynamically-loading event image; same on both sites -- not a regression |

(Note: button-link and video each produced one of the three first-attempt
failures; video recovered on retry, so the end-state failures were button-link
and view.)

## Triaged findings

### [1] button-link (Chromium) -- transient server error, not a regression

During the run, every attempt (3 retries) of the v2230 request for this page
returned a **PHP fatal error white-screen** instead of the page:

```
Warning: require_once(/code/web/autoload.php): Failed to open stream:
No such file or directory in /code/web/index.php on line 14
Fatal error: Uncaught Error: Failed opening required '/code/web/autoload.php' ...
```

This is a transient Pantheon container condition (the `autoload.php` bootstrap
file is momentarily absent while the sandbox container restarts/deploys), not a
property of the v2230 build. **Re-fetched live during triage, the page renders
correctly** with the full Button Link component (Design Options, Section Theme
1-4, all button variants), matching the dev baseline. The same component passed
cleanly on Firefox, WebKit, and Mobile Safari.

- Baseline (dev): https://dev-ys-yalesites-visreg-yale-edu.pantheonsite.io/component-pages-for-e2e-testing/button-link
- Candidate (v2230): https://v2230-ys-yalesites-visreg-yale-edu.pantheonsite.io/component-pages-for-e2e-testing/button-link
- Artifacts: `reports/artifacts/button-link-chromium-v2230-actual-ERROR.png` (the error screen captured), `reports/artifacts/button-link-chromium-diff.png`

**Action:** None required for the release. (Optional: worth a quick re-confirm
that v2230 stays stable, since the sandbox erroring under load is a sandbox
artifact, not a code change.)

### [2] video (Chromium) -- third-party embed timing, not a regression

The only differing region was the embedded **YouTube video thumbnail**
("What is Drupal?" poster frame) inside the video player iframe. The surrounding
component (heading, teaser text, layout) matched. The test was **flaky**: it
failed once because the YouTube thumbnail had not finished loading, then passed
on retry once it loaded. This is third-party embed content controlled by
YouTube, not YaleSites markup, and is expected to vary by load timing.

- Baseline (dev): https://dev-ys-yalesites-visreg-yale-edu.pantheonsite.io/component-pages-for-e2e-testing/video
- Candidate (v2230): https://v2230-ys-yalesites-visreg-yale-edu.pantheonsite.io/component-pages-for-e2e-testing/video
- Artifact: `reports/artifacts/video-chromium-diff.png`

**Action:** None. (Optional hardening: mask the embed region for future runs.)

### [3] view (WebKit) -- unstable screenshot capture, not a regression

On WebKit only, Playwright could not capture two consecutive identical frames of
this page within the stabilization window (even after raising it to 20s). The
instability is isolated to the second event card's image in the event listing,
which loads/repaints progressively on WebKit. This behaviour is identical on
**both** the dev baseline and v2230 (the baseline also failed to stabilize on
WebKit), so it is a test-harness limitation on that page/engine, not a
difference introduced by v2230. The `view` component matched cleanly on
Chromium, Firefox, and Mobile Safari.

- Baseline (dev): https://dev-ys-yalesites-visreg-yale-edu.pantheonsite.io/component-pages-for-e2e-testing/view
- Candidate (v2230): https://v2230-ys-yalesites-visreg-yale-edu.pantheonsite.io/component-pages-for-e2e-testing/view
- Artifact: `reports/artifacts/view-webkit-diff.png`

**Action:** None required for the release. (Optional hardening: mask or
explicitly pre-load the event listing image for future WebKit runs.)

## How to reproduce the run

From `yalesites-automated-tests` on branch `visreg-dev-vs-v2230`:

```bash
# One-shot wrapper (warms sandboxes, captures dev baseline, compares v2230):
./scripts/compareSites.sh

# Or manually:
DEV="https://dev-ys-yalesites-visreg-yale-edu.pantheonsite.io"
V2230="https://v2230-ys-yalesites-visreg-yale-edu.pantheonsite.io"
YALESITES_URL="$DEV"   npx playwright test all-vis-reg.spec --update-snapshots
YALESITES_URL="$V2230" npx playwright test all-vis-reg.spec --reporter=html,json
npx playwright show-report
```

Baseline snapshots live in `snapshots/all-vis-reg.spec.ts-snapshots/`. The
candidate run writes per-page diff/actual/expected PNGs under `test-results/`
for any page that differs.

## Notes / caveats

- The two Pantheon sandbox environments idle down and are slow to warm; the
  harness was hardened for this (90s navigation timeout, 180s per-test budget,
  2 retries, single worker, network/font/image load waits, a warm-up curl). The
  one hard failure (button-link) was nonetheless a transient sandbox restart, not
  a code regression -- worth keeping in mind that sandbox flakiness, not v2230,
  produced it.
- Scope was the 30 component test pages only (per request). The 24 real content
  pages in the sitemap (home, events, posts, profiles, etc.) were not compared.
- Only the two approved domains were ever requested. No third-party domains were
  scanned; the YouTube thumbnail in [2] is embedded content rendered in-page, not
  a separate scan target.
